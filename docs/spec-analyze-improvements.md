## 概要

Analyze ビューの**現状仕様**は `docs/spec-overview.md` の「ビュー」表に記載がある。
本書はそこに書かれていない**未実装の改善案**をまとめたもので、現状の記述ではない。
実装したものは本書から削除し、`docs/spec-overview.md` 側を更新する。

現行実装は「時系列の描画」としては作り込まれている (欠測の破線処理、目標線の
窓非依存性、確定点キャッシュの分割)。伸びしろは描画精度ではなく、次の 3 方向にある。

1. **内訳タブが単軸で止まっている** — 軸の解放 (G-01) は完了。クロス集計とドリルダウンが残る。
2. **「なぜ動いたか」に到達できない** — コミットのツールチップ表示 (G-03) とキーボード
   操作 (G-02) は完了。バケット間の差分と固定カーソルが残る。
3. **指標が「残件数」1 種類しかない** — 流入/流出・サイクルタイム・PR は未対応。

## 第 1 波: 既存コードの延長で完結するもの

### G-04 取得時刻の表示と手動リフレッシュ

#### 現状

確定済みバケットは `staleTime: Infinity`、進行中バケットは 5 分 (`OPEN_POINT_STALE_TIME`) で
キャッシュされる (`useAnalyzeQueries.ts`)。これは合理的だが、
**画面上に「いつ時点のデータか」を示す表示が無く、即時更新する手段も無い**。
数字を見て判断する画面としては、鮮度が不明なまま読むリスクがある。

#### 変更内容

グループヘッダーの期間表示の隣に最終取得時刻を出し、リフレッシュボタンを置く。
押下時は進行中バケットと内訳のクエリキーを invalidate する。
確定済みバケットは定義上変化しないため invalidate しない
(再取得すると窓が広いほど無駄が大きい)。

#### 影響ファイル

- `src/features/analyze/AnalyzeView.tsx` — ボタンと invalidate 配線
- `src/features/analyze/useAnalyzeQueries.ts` — `dataUpdatedAt` の集約を返す

#### 完了条件

- 最終取得時刻が表示され、リフレッシュで更新される
- リフレッシュしても確定済みバケットの再取得が発生しない
- ボタンにキーボードで到達でき、`AnalyzeShortcutHints` に記載がある

### G-06 チャート高さの可変化

#### 現状

`AnalyzeCombinedChart.tsx` の `<svg>` は `className="block h-[15rem]"` の固定高で、
`preserveAspectRatio="none"` が併用されている。
ウィンドウを縦に広げても描画領域は 15rem のままで、横だけが伸びる。
`AGENTS.md` の「操作系画面では余白を減らし、利用可能な高さをグリッド・プレビューに使う」
方針と噛み合っていない。

なお `preserveAspectRatio="none"` 自体は viewBox (720×260) を
コンテナ幅へ引き伸ばす前提の設計であり、フォントやストローク幅も一緒に歪む。
高さを可変にするならこの前提から見直す必要がある。

#### 変更内容

コンテナの実測サイズ (`ResizeObserver`) を viewBox に反映し、
`preserveAspectRatio` の指定を外す。高さは `clamp` で下限 15rem / 上限 28rem 程度に収める。
テキスト・ストローク幅が歪まなくなるため、既存の `text-[9px]` 等の
見た目調整も併せて確認する。

#### 影響ファイル

- `src/features/analyze/AnalyzeCombinedChart.tsx`
- `src/features/analyze/analyzeChartLayout.ts` — `CHART_VIEWBOX` の可変化

#### 完了条件

- ウィンドウを縦に広げるとチャートも高くなる
- 横に広げても線の太さと文字サイズが変わらない
- 既存の `analyzeChartLayout.test.ts` が通る (viewBox を引数で渡す設計は現状維持)

> 注: 本項目と G-05 は実機での見た目確認が必須。静的なコード読解だけでは
> 崩れの有無を判断できない。

## 第 2 波: 分析価値の本体

### G-07 内訳の 2 軸クロス集計 (積み上げ棒)

#### 現状

内訳は単軸の横棒のみ。「担当者ごとの件数」は分かるが、
**その中身が何で詰まっているか**が分からない。
22 件抱えている人の内訳が Active 中心なのか Blocked 中心なのかで、
必要な対応がまったく変わる。

#### 変更内容

主軸 (行) と副軸 (積み上げの分割) の 2 つを選び、横棒を副軸の値で塗り分ける。
`buildBreakdown()` を拡張するのではなく、`buildCrossBreakdown(items, primary, secondary)`
を新設する (単軸のシンプルさを壊さないため)。

副軸は「なし」を既定とし、選んだときだけ積み上げになる。
副軸の色は状態・種別に応じた固定マップを用意する
(`analyzeColors.ts` の位置ベース割り当てとは別。状態は意味を持つため、
Blocked が毎回違う色になるのは避ける)。

副軸の値数は 6 程度で打ち切り、超過分は「その他」に畳む。

#### 影響ファイル

- `src/features/analyze/analyzeBreakdown.ts` — `buildCrossBreakdown()` の追加
- `src/features/analyze/analyzeColors.ts` — 状態 / 種別の意味的カラーマップ
- `src/features/analyze/AnalyzeBreakdownPanel.tsx` — 積み上げ描画と副軸セレクタ

#### 完了条件

- 担当者 × 状態で、行ごとに状態別の内訳が塗り分けられる
- 積み上げの合計が行の総数と一致する
- 副軸「なし」で現行と同じ単色の棒に戻る
- 凡例が副軸の値を示し、キーボードで到達できる

### G-08 内訳バーからのドリルダウン

#### 現状

内訳の行は `<li>` で、フォーカス移動 (`↑↓`/`J K`/`Home`/`End`) はできるが
**選択して先へ進む操作が無い**。件数を見て終わりで、その中身にたどり着けない。

#### 変更内容

行を選択可能にし、`Enter` でその値に該当する作業項目の一覧を開く。
`useBreakdownItems` が返す `items` を絞り込むだけなので追加取得は発生しない。

一覧は推移タブの明細と同様に、`Esc` で内訳へ戻る。戻り先のフォーカスは
元の行に復帰させる (`AGENTS.md` のフォーカス返却要件)。
各項目は既存の作業項目行と同様に、ブラウザで開くリンクを持つ。

G-07 実装後は、積み上げのセグメント単位 (担当者 × 状態の交点) での
ドリルダウンも同じ経路で扱えるようにする。

#### 影響ファイル

- `src/features/analyze/AnalyzeBreakdownPanel.tsx` — 選択と遷移
- `src/features/analyze/AnalyzeDetailPanels.tsx` — 内訳明細パネルの追加
- `src/features/analyze/AnalyzeView.tsx` — `AnalyzeSelection` に内訳用の種別を追加

#### 完了条件

- 内訳の行から作業項目一覧へ遷移し、`Esc` で元の行にフォーカスが戻る
- 一覧の件数が棒の件数と一致する
- 「その他」行は畳まれた複数値の集合のため、ドリルダウン対象外とする (現行の `isOther` を利用)

### G-09 共有カーソルのピン留め

#### 現状

`useSharedCursor` はポインタが離れると `onPointerLeave` で `null` に戻る。
ツールチップの値を読みながら他の要素を操作できず、
ツールチップ自体も `pointer-events-none` のため中身を選択できない。

#### 変更内容

カーソルに「固定」状態を持たせる。クリック (またはキーボードの `Enter`) で固定し、
固定中は `onPointerLeave` で消えない。`Esc` または再クリックで解除。
固定中はツールチップの `pointer-events` を有効化し、実装済みのコミット表示 (G-03) から
ブランチ明細への遷移リンクを張れるようにする。

固定中であることが分かる表示 (ピンアイコン + 解除キーの案内) を出す。

#### 影響ファイル

- `src/features/analyze/AnalyzeCombinedChart.tsx` — `useSharedCursor` の状態拡張
- `src/features/analyze/AnalyzeTrendPanel.tsx` — ツールチップの `pointer-events` 切替

#### 完了条件

- 固定するとポインタを外してもカーソルとツールチップが残る
- 固定中もサマリー行の数値がその時点に追従したままになる
- `Esc` で解除され、フォーカスがチャートに残る
- 期間や粒度を変えたとき、範囲外になった固定カーソルが解除される
  (現行 `useSharedCursor` の範囲外クランプと同じ扱い)

### G-10 異常値の自動マーク

#### 現状

山や谷は目視で探すしかない。90 日窓では見落としが起きる。

#### 変更内容

各バケットの前期比を求め、その系列の過去分布から外れた点にマーカーを打つ。
判定は中央値絶対偏差 (MAD) ベースとする — 標準偏差は外れ値自身に引きずられるため、
異常検出には向かない。しきい値は「MAD の 3 倍」程度を既定とする。

欠測 (`count: null`) を挟む区間は前期比を計算しない (`valueWithPrevious` は
直近の非 null を探すが、間隔が空いた差分を異常と判定するのは誤り)。

マーカーはカーソルを合わせたときにツールチップで「前期比 +13 (通常の変動幅を超過)」
のように理由を示す。系列数が多いときにマーカーで埋まらないよう、
1 系列あたり上位 3 点までに制限する。

#### 影響ファイル

- `src/features/analyze/analyzeChartLayout.ts` または新規 `analyzeOutliers.ts`
- `src/features/analyze/AnalyzeCombinedChart.tsx` — マーカー描画
- `src/features/analyze/AnalyzeChartLegend.tsx` — ツールチップの理由表示

#### 完了条件

- 明らかな跳ねにマーカーが付き、平坦な系列には付かない
- 欠測を挟んだ区間が異常判定されない
- 新規 `analyzeOutliers.test.ts` で判定ロジックを検証

### G-11 予測着地点の外挿

#### 現状

マイルストーン目標線 (`analyzeMilestones.ts`) は「どこへ向かうべきか」を描くが、
「このペースならいつ着くか」は出ない。目標との乖離は現時点の差分しか分からない。

#### 変更内容

直近 N 期 (既定 6、粒度に応じて調整) の傾きを最小二乗で求め、
チャート右側へ破線で外挿する。件数が 0 に到達する日を「予測着地」として表示し、
最後のマイルストーンと比較して「目標より N 日遅れ / 前倒し」を出す。

傾きが 0 以上 (減っていない) 場合は着地日を出さず、「現ペースでは到達しない」と表示する。
外挿はあくまで直線であり、根拠の弱さが伝わる表示にする (破線 + 中空の終点)。

#### 影響ファイル

- 新規 `src/features/analyze/analyzeForecast.ts`
- `src/features/analyze/AnalyzeCombinedChart.tsx` — 外挿線の描画
- `src/features/analyze/AnalyzeMilestonePanel.tsx` — 目標との差の表示

#### 完了条件

- 減少傾向の系列で着地日が出て、マイルストーンとの日数差が表示される
- 増加傾向・横ばいの系列で着地日を出さない
- 外挿線が実測線と視覚的に区別できる
- `analyzeForecast.test.ts` で傾き算出と到達日を検証

### G-14 履歴の SQLite 永続化

#### 現状

ASOF サンプリング結果は TanStack Query のセッションキャッシュのみに存在する
(`CLOSED_POINT_GC_TIME = 60 * 60_000`)。アプリを再起動すると全点を取り直す。
確定済みバケットの件数は定義上二度と変わらないにもかかわらず、
起動のたびに 90 点 × クエリ数の API 呼び出しが発生しうる。

#### 変更内容

確定済みサンプルを SQLite に保存する。テーブルは
`(organization_id, project_id, wiql_hash, timestamp) → count` を主キーとし、
`wiql_hash` は WIQL 文字列のハッシュ (WIQL を変えたら別系列として扱うため)。

読み出しはローカル優先、欠けている点のみ API で埋める。
`db.rs` の `migrate()` に新しい番号付きステップを追加し、
`SCHEMA_VERSION` (現在 19) を上げる。既存ステップは編集しない。

キャッシュの破棄手段は Settings のキャッシュ操作に合わせる。

#### 新規 IPC

| コマンド | 入力 | 出力 |
|---|---|---|
| `read_analyze_history` | org / project / wiqlHash / timestamps | 保存済みの点 (欠けは null) |
| `write_analyze_history` | org / project / wiqlHash / points | 保存件数 |

`count_work_item_query_history` は現行のまま残し、埋め合わせ取得に使う。

#### 影響ファイル

- `src-tauri/src/db/mod.rs` — `SCHEMA_VERSION` の更新
- `src-tauri/src/db/migrate.rs` — 新規テーブル
- `src-tauri/src/work_items/` — 履歴の読み書き
- `src-tauri/src/commands/work_items.rs`, `src-tauri/src/lib.rs`
- `src/lib/azdoCommands.ts` (+ `src/lib/commands/workItems.ts`, `src/lib/azdoDemo.ts`)
- `src/features/analyze/useAnalyzeQueries.ts`

#### 完了条件

- 再起動後、確定済み期間が API 呼び出しなしで即描画される
- WIQL を編集すると別系列として扱われ、古い値が混ざらない
- `migrate()` が繰り返し実行可能である (既存の方針どおり)
- `cargo test --workspace` が通る

### G-15 流入 / 流出 (created vs closed) の対比

#### 現状

残件数の折れ線だけでは、
「捌けていないのか、そもそも流入が増えているのか」を区別できない。
運用判断としてはこの区別のほうが重要な場面が多い。

#### 変更内容

期間ごとの作成件数とクローズ件数を取得し、
基準線の上下に振り分けた棒として描く。残件数の折れ線と重ねると、
「流入が流出を上回り続けている期間」が視覚的に判別できる。

WIQL の `System.CreatedDate` / `Microsoft.VSTS.Common.ClosedDate` を
期間で絞る形になるため、ASOF サンプリングとは別の取得経路になる。

#### 新規 IPC

`count_work_item_flow` — グループのクエリ条件と期間リストを受け取り、
バケットごとの `{ created, closed }` を返す。

#### 完了条件

- 流入・流出の棒が残件数の折れ線と同じ時間軸で重なる
- クローズ日を持たない作業項目が流出に数えられない
- デモモードで妥当な形の値が返る

---

### G-16 サイクルタイム / リードタイム

#### 現状

「件数」しか測れていない。滞留の長さは見えない。

#### 変更内容

作業項目の状態遷移履歴から、Active → Closed の所要日数を求め、
バケットごとの中央値を折れ線で描く。
平均ではなく中央値とする (長期滞留の 1 件に引きずられないため)。

Azure DevOps の `workItems/{id}/updates` を辿る必要があり、
件数が多いと API 呼び出しが嵩む。取得対象の上限と、
`crates/azdo-client/` 側でのレート配慮 (既存の `get_json` 経路を使う) が前提。

#### 新規 IPC

`compute_work_item_cycle_time` — クエリ条件と期間から、バケット別の統計を返す。

#### 完了条件

- サイクルタイムの推移が描画され、件数系列と別軸で読める
- 未クローズ項目が計算対象から除外される
- `crates/azdo-client/` に `wiremock` ベースのテストを追加

---

### G-17 PR 系列メンバーの追加

#### 現状

グループのメンバーはクエリとブランチの 2 種類のみ
(`AnalyzeQueryMember` / `AnalyzeBranchMember`)。
開発の動きとして最も情報量のある PR が対象外になっている。

#### 変更内容

`AnalyzePullRequestMember` を追加し、作成数 / マージ数 / レビュー待ち時間を
系列として描けるようにする。

**制約**: `AGENTS.md` と `docs/spec-overview.md` の方針により、
PR ビューはローカル同期された **active** PR データで動作し、
「全ステータス」を示唆する UI を出してはならない。
マージ済み PR の履歴集計は、サービスとキャッシュ層を同時に更新するまで実現できない。
したがって本項目は `docs/spec-reliability-foundation.md` の **F-37**
(active 以外の PR の限定取得) に依存する。F-37 の完了前に着手しない。

#### 完了条件

- F-37 完了後に着手し、PR 系列がクエリ・ブランチと同じ時間軸に重なる
- メンバー上限 (`MAX_ANALYZE_GROUP_MEMBERS = 12`) の配分に PR を含める
- 未対応のステータス範囲を示唆する UI を出さない

---

### G-18 内訳の集計をバックエンドへ移動

#### 現状

内訳は `run_work_item_query` で**作業項目の行そのもの**を最大 500 件
(`BREAKDOWN_ITEM_LIMIT`) 取得し、フロントで数えている。
上限に達すると「一部のみの内訳」と赤字で警告するが、
警告が出た時点でその画面の数字は判断に使えない。

#### 変更内容

集計をバックエンドへ移し、行ではなく**集計結果**を返す。
これにより上限そのものが不要になり、転送量も大幅に減る。
G-07 のクロス集計も同じ経路で扱える。

ただし G-08 のドリルダウンは行データを必要とするため、
「集計は集計コマンド、ドリルダウン時のみ行取得」という二段構成にする。

#### 新規 IPC

`aggregate_work_item_query` — WIQL と集計軸 (1〜2 個) を受け取り、
`{ key, subKey, count }[]` を返す。

#### 完了条件

- 500 件を超える結果でも正確な内訳が出て、警告表示が不要になる
- 合計が推移タブの件数と一致する (現行の重複排除と同じ同一性判定を維持)
- ドリルダウン時のみ行を取得する

## 検証方針

`AGENTS.md` の検証チェックリストに従う。本カテゴリで特に必要なもの:

- フロントエンドのみの項目 (G-04〜G-13): `pnpm tsc --noEmit` と `pnpm test -- --run`
- キーボード操作を含む項目 (G-08, G-09): 実機での通し確認。
  クリック経路が動くことの確認だけでは不十分
- レイアウトに関わる項目 (G-05, G-06): 実機での見た目確認が必須
- バックエンドを伴う項目 (G-14〜G-18): `cargo test --workspace` と
  `cargo clippy --workspace --all-targets -- -D warnings`、
  REST 挙動の変更は `crates/azdo-client/` に `wiremock` テスト
- 全項目共通: ブラウザデモモードが健全であること
  (`azdoCommands.ts` のデモ分岐は必須作業であり、仕上げではない)

実装した項目は本書から削除し、`docs/spec-overview.md` の Analyze の記述を
同じ変更の中で更新する。
