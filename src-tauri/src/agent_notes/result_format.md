# DevDeck の結果 HTML の書き方

Work Item の調査結果と Pull Request のレビュー結果を、DevDeck のプレビューで読みやすい 1 枚の HTML にする手順。
読む人は一覧と並べた細いペインで、数十秒で「結論」と「どこを見ればよいか」を掴みたい。文章より図と表で伝える。

## 置き場所とファイル名

| 対象 | フォルダ | ファイル名 |
| --- | --- | --- |
| Pull Request のレビュー | 設定の Review result folder | `PR{番号}.html` (例: `PR1234.html`) |
| Work Item の調査 | 設定の Work item result folder | `WIT{番号}.html` (例: `WIT5678.html`) |

- やり直すときは同じファイルを上書きする (DevDeck は番号が合うファイルのうち更新日時が新しいものを出す)。
- 1 ファイル 5 MB まで。超えると表示されない。

## プレビューの制約 (守らないと表示が崩れる)

- **JavaScript は動かない** (サンドボックスの iframe)。Mermaid・Chart.js などは使えない。図はすべて **インライン SVG** か HTML + CSS で描く。
- **外部ファイルを読まない**。CSS は `<style>`、画像は SVG か `data:` URI で埋め込む。CDN・Web フォントは使わない。
- 幅は 360px〜900px 程度で変わる。横スクロールを出さない (表と SVG は `max-width: 100%`、SVG は `viewBox` を付けて幅を指定しない)。
- ライト / ダーク両方で読めるようにする。色は `:root` の変数にまとめ、`@media (prefers-color-scheme: dark)` で切り替える。SVG の線・文字も変数か `currentColor` を使う。
- 人が直してほしい箇所を選んでコメントするので、段落・表の行・図は要素ごとに分けて書く (1 つの巨大な `<pre>` にしない)。

## 共通の骨組み

上から順に並べる。各章の見出しは `<h2>`。

1. **ヘッダー**: `!番号 タイトル` / `#番号 タイトル`、判定バッジ、作成日時、対象 (リポジトリ・ブランチ / 種類・状態)。番号は対象の PR / Work Item へのリンクにする (`context_file` の `URL` を `<a href>` に使う。DevDeck はリンクを既定のブラウザで開く)。本文で触れる関連 PR / Work Item もリンクにする。
2. **結論 (3 行以内)**: 判定と理由。最初の画面で読み終わる長さ。
3. **ポイントの図**: 結論を 1 枚で示す図 (下の「図の選び方」)。
4. **本文**: PR / WI ごとの章 (下記)。各章に図か表を最低 1 つ。
5. **根拠**: `file:line` とコードの抜粋。推測は `unverified` のバッジを付けて分ける。
6. **未確認・前提**: 確かめられなかったこと、置いた前提。
7. **指摘の下書き** (PR のみ): 畳んだ状態で最後に置く (下記)。

判定バッジは色と文字の両方で示す (色だけに頼らない)。

## Pull Request のレビュー

| 章 | 中身 | 図・表 |
| --- | --- | --- |
| 判定 | `Approve` / `Approve with suggestions` / `Wait for author` / `Reject` のどれか 1 つ | バッジ |
| 変更の全体像 | どのモジュール・ファイルが、どう呼び合うように変わったか | **変更マップ** (変更箇所を色付きの箱、呼び出しを矢印。リスクの高い箱を強調) |
| 指摘一覧 | 重要度 (`Must` / `Should` / `Nit`)・場所・内容・提案 | 表 (重要度順) |
| 指摘の詳細 | 1 指摘 1 ブロック。何が起きるか、どう直すか | 流れが関わる指摘は **Before / After 図** か **シーケンス図**。コード抜粋 |
| リスク | 影響の大きさ × 起きやすさ | **2×2 マトリクス** に指摘番号を置く |
| テスト観点 | 足りないテスト・手で確かめること | チェックリスト |
| 指摘の下書き | 指摘ごとに、PR のコメントへそのまま貼れる文面 | 末尾に置き、閉じた `<details>` で畳む |

指摘の下書き:

- 「未確認・前提」の後、HTML の最後に `<details>` (`open` を付けない) で置く。`<summary>` は `指摘の下書き (N 件)`。
- 指摘一覧と同じ番号・重要度・`file:line` を見出しにし、その下に文面を段落で書く (`<pre>` にしない)。
- 文面は PR の作者に宛てて書く。何が起きるか → どう直してほしいか、の順に 1〜3 文。丁寧語で、命令口調にしない。
- 下書きを置くだけで、PR には投稿しない (投稿するかは人が決める)。

## Work Item の調査

| 章 | 中身 | 図・表 |
| --- | --- | --- |
| 判定 | `原因特定` / `原因候補あり` / `要追加情報` / `仕様どおり` のどれか 1 つ (要望なら `実装方針あり` / `要相談`) | バッジ |
| 何が起きているか | 再現条件・期待と実際 | **処理フロー図** で問題の起きる箇所を強調 (バグ)、**現状 → 目標** の図 (要望) |
| 原因 | どのコードが、なぜそうなるか | **シーケンス図** か **データの流れ図**。コード抜粋 |
| 影響範囲 | 他に同じ原因で壊れる所・関係するモジュール | **影響マップ** (中心に原因、周りに影響先) |
| 対応案 | 2〜3 案と推奨 | 比較表 (工数・リスク・影響範囲)。推奨を明示 |
| 次のアクション | 誰が何をするか | チェックリスト |

## 図の選び方

| 伝えたいこと | 図 |
| --- | --- |
| 処理の順番・分岐・どこで失敗するか | フロー図 (箱と矢印、失敗箇所を強調色) |
| 複数の部品のやり取り・タイミング | シーケンス図 (縦の線 = 部品、横の矢印 = 呼び出し) |
| 変更前と変更後の違い | Before / After を左右 (狭い幅では上下) に並べる |
| 構成・依存・影響の広がり | 箱と矢印のマップ |
| 優先度・リスクの比較 | 2×2 マトリクス |
| 時系列 (発生・変更・デプロイ) | タイムライン |
| 数の比較 | 横棒 (SVG の `rect`) |

図の描き方:

- 1 枚に言いたいことは 1 つ。図の下に「この図で見ること」を 1 行で書く (`<figcaption>`)。
- 強調は 1 色 (問題・変更箇所) だけ。他は中立色。飾りの影・グラデーションは使わない。
- 文字は 12px 相当以上。箱の中の文字は短く (ファイル名・関数名・3〜5 語)。
- 図の中の名前 (関数・ファイル) は本文と同じ表記にし、本文の `file:line` と対応が取れるようにする。
- 実際に確かめた事実だけを図にする。推測の矢印は点線にして `unverified` と書く。

## 文章

- Note の言語で書く (日本語の Note には日本語)。結論を先に、1 文を短く。
- 経過 (何を調べたか) は書かない。分かったことと根拠だけ。
- 秘密情報 (PAT・トークン・接続文字列) を書かない。
- Note の `fix` で直した要素には `data-agent-note="{Note のファイル名}"` を付ける (DevDeck が直した箇所として示す)。
