# DevDeck の Pull Request レビュー

このファイルはあなた (利用者) が編集する正本です。DevDeck は初回に置くだけで、以後は上書きしません。結果 HTML の置き場所・プレビューの制約・共通の骨組み・図の描き方は、結果フォルダの `AGENTS.md` の「DevDeck の結果 HTML の書き方」に従い、PR 固有の部分はこのファイルに従います。

## 観点 (優先順)

1. 正しさ: バグ・境界条件・エラー処理・並行性
2. セキュリティ: 入力検証・認可・秘密情報
3. テスト: 変更に見合うテストがあるか
4. 既存コードや規約との整合
5. 保守性

- 指摘の対象は差分の中に限る。呼び出し元や前提を確かめるために、手元のクローンで周辺コードを読んでよい。
- 実際にそうなると確かめた指摘だけを `Must` / `Should` にする。確信が持てないものは `unverified` に分ける。
- 好みや些末な書式は `Nit` に留め、指摘を水増ししない。問題が見つからなければ、見つからなかったと根拠を添えて書く。

## 変更の種類を決める

PR の説明・ブランチ名・コミット・差分から、変更を次のどれかに分ける。両方を含む PR は両方の章を置く。決めきれないときは分け方に `unverified` を付ける。

- **機能追加**: 利用者や呼び出し側に、新しくできることが増える
- **バグ修正**: 誤った動きを正す
- **その他**: リファクタリング・設定・依存の更新・テストだけの変更

## 章立て

| 章 | 中身 | 図・表 |
| --- | --- | --- |
| 判定 | `Approve` / `Approve with suggestions` / `Wait for author` / `Reject` のどれか 1 つ | バッジ |
| 追加された機能 (機能追加のとき) | 何ができるようになったか、入口 (画面・API・コマンド) から新しい部品・データまでのつながり | **機能の構成図**: 入口 → 処理 → データの箱と矢印。新しく足した箱と矢印だけを強調色にし、既存の部品は中立色で残す |
| バグの起きる仕組み (バグ修正のとき) | どの入力・条件で、どの段で、何が壊れていたか | **フロー図かシーケンス図**: 問題の起きる段だけを強調色にし、壊れる条件を矢印のラベルに書く |
| 直し方 (バグ修正のとき) | 修正がどの段をどう変えたか、原因に届いているか (症状だけを抑えていないか) | **Before / After 図**: 上の図と同じ配置で並べ、変わった段だけを強調色にする |
| 変更マップ (その他のとき) | どのモジュール・ファイルが、どう呼び合うように変わったか | 変更箇所を色付きの箱、呼び出しを矢印。リスクの高い箱を強調 |
| 指摘一覧 | 重要度 (`Must` / `Should` / `Nit`)・場所・内容・提案 | 表 (重要度順) |
| 指摘の詳細 | 1 指摘 1 ブロック。何が起きるか、どう直すか、根拠 (`file:line` とコード抜粋、推測は `unverified`) | 流れが関わる指摘は Before / After 図かシーケンス図。コード抜粋 |
| リスク | 影響の大きさ × 起きやすさ | 2×2 マトリクスに指摘番号を置く |
| テスト観点 | 足りないテスト・手で確かめること | チェックリスト |
| 指摘の下書き | 指摘ごとに、PR のコメントへそのまま貼れる文面 | 末尾に置き、閉じた `<details>` で畳む |

- 「追加された機能」「バグの起きる仕組み」「直し方」の図は、差分とコードで確かめた部品と流れだけで描く。推測の矢印は点線にして `unverified` と書く。
- バグ修正では、「バグの起きる仕組み」と「直し方」の図を同じ部品・同じ並びで描き、見比べて変わった箇所が分かるようにする。修正が原因に届いていないと判断したら、その段を図の中で示し、指摘にも挙げる。
- ポイントの図 (結論の直後の 1 枚) は、機能追加なら機能の構成図、バグ修正なら直し方の Before / After 図を兼ねてよい。同じ図を 2 回置かない。
- 同じ指摘を何度も書かない。指摘一覧は 1 行の要約、指摘の詳細は中身と根拠、指摘の下書きは作者に宛てた文面で、それぞれ役割が違う。独立した「根拠」の章は置かない。
- 小さい PR (変更が 2 ファイル以下で、`Must` の指摘が無い) では「変更マップ」と「リスク」の章を省く。「追加された機能」「バグの起きる仕組み」「直し方」は小さい PR でも省かない。

## 指摘の場所のリンク

指摘一覧の「場所」と、指摘の詳細の `file:line` に付ける。

- PR の Files タブでそのファイルを開くリンクにする。DevDeck はリンクを既定のブラウザで開く。材料は `context_file` の `URL` (`{組織}/{プロジェクト}/_git/{リポジトリ}/pullrequest/{番号}`) と変更ファイルのパス。
- リンクの形: `{PR の URL}?_a=files&path={パス}&line={開始行}&lineStartColumn=1&lineEnd={終了行 + 1}&lineEndColumn=1`。
- `{パス}` は `/` を `%2F` にして URL エンコードする。行が決められない指摘 (ファイル全体など) は `line` 系を付けず `?_a=files&path={パス}` だけにする。
- 材料のどれかが分からないときは、推測でリンクを作らず、文字だけにする。

## 指摘の下書き

- 「未確認・前提」の後、HTML の最後に `<details>` (`open` を付けない) で置く。`<summary>` は `指摘の下書き (N 件)`。
- 指摘一覧と同じ番号・重要度・`file:line` を見出しにし、その下に文面を段落で書く (`<pre>` にしない)。
- 文面は PR の作者に宛てて書く。何が起きるか → どう直してほしいか、の順に 1〜3 文。丁寧語で、命令口調にしない。
- 下書きを置くだけで、PR には投稿しない (投稿するかは人が決める)。
