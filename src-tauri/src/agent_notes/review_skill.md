# DevDeck の Pull Request レビュー

このファイルはあなた (利用者) が編集する正本です。DevDeck は初回に置くだけで、以後は上書きしません。結果 HTML の置き場所・プレビューの制約・共通の骨組み・図の描き方は、結果フォルダの `AGENTS.md` の「DevDeck の結果 HTML の書き方」に従い、PR 固有の部分はこのファイルに従います。

## 観点 (優先順)

1. 正しさ: バグ・境界条件・エラー処理・並行性
2. セキュリティ: 入力検証・認可・秘密情報
3. テスト: 変更に見合うテストがあるか (足りなければ指摘にする)
4. 既存コードや規約との整合
5. 保守性

- 指摘の対象は差分の中に限る。呼び出し元や前提を確かめるために、手元のクローンで周辺コードを読んでよい。
- 実際にそうなると確かめた指摘だけを `Must` / `Should` にする。確信が持てないものは `unverified` に分ける。
- 好みや些末な書式は `Nit` に留め、指摘を水増ししない。問題が見つからなければ、見つからなかったと根拠を添えて書く。

## 変更の種類を決める

PR の説明・ブランチ名・コミット・差分から、変更を次のどれかに分ける。両方を含む PR は両方の章を置く。決めきれないときは分け方に `unverified` を付ける。

- **機能追加**: 利用者や呼び出し側に、新しくできることが増える
- **バグ修正**: 誤った動きを正す
- **その他**: リファクタリング・設定・依存の更新・テストだけの変更

## 章立て

読む人が最初の画面で「判定」と「どこを直すか」を掴めるようにする。経過・言い換え・指摘の無い章は書かない。全体で画面 2〜3 枚に収める。

| 章 | 中身 | 図・表 |
| --- | --- | --- |
| 判定と結論 | `Approve` / `Approve with suggestions` / `Wait for author` / `Reject` のどれか 1 つと、理由を 3 行以内 | バッジ |
| ポイントの図 | PR が何を変えたかを 1 枚で示す。機能追加は構成図 (入口 → 処理 → データ、足した箱と矢印だけ強調色)、バグ修正は Before / After (壊れていた段と変えた段だけ強調色、原因に届いているかが分かるように)、その他は変更マップ | 図 1 枚 |
| 指摘一覧 | 重要度 (`Must` / `Should` / `Nit` / `unverified`)・場所・内容 1 行。重要度順 | 表 |
| 指摘の詳細 | `Must` と `Should` だけ。1 指摘 2〜3 文 (何が起きるか、どう直すか) と、要るときだけ 10 行以内のコード抜粋 | 抜粋 |

- 図は合計 2 枚まで (ポイントの図と、流れを見ないと分からない指摘の 1 枚)。リスクのマトリクスは描かない。
- 図は差分とコードで確かめた部品と流れだけで描く。推測の矢印は点線にして `unverified` と書く。
- `Nit` と `unverified` は一覧の 1 行だけにし、詳細を書かない。
- 共通の骨組みの「未確認・前提」には、一覧の `unverified` に書いていないことだけを書く。無ければ章ごと省く。
- 同じ指摘を何度も書かない。一覧は 1 行の要約、詳細は中身と根拠、リンクのコメントは作者に宛てた短い文面。独立した「根拠」の章は置かない。

## 指摘の場所のリンク

指摘一覧の「場所」と、指摘の詳細の `file:line` に付ける。

- PR の Files タブでそのファイルを開くリンクにする。DevDeck はリンクを既定のブラウザで開く。材料は `context_file` の `URL` (`{組織}/{プロジェクト}/_git/{リポジトリ}/pullrequest/{番号}`) と変更ファイルのパス。
- リンクの形: `{PR の URL}?_a=files&path={パス}&line={開始行}&lineStartColumn=1&lineEnd={終了行 + 1}&lineEndColumn=1`。
- `{パス}` は `/` を `%2F` にして URL エンコードする。行が決められない指摘 (ファイル全体など) は `line` 系を付けず `?_a=files&path={パス}` だけにする。
- 材料のどれかが分からないときは、推測でリンクを作らず、文字だけにする。

## PR に投稿するコメント

指摘一覧の「場所」のリンクに `data-ado-comment` 属性で、その行へ投稿するコメントを入れる。DevDeck ではリンクを押すと、このコメントを PR のその行のスレッドとして投稿し、Files タブを開く。2 回目以降のクリックは開くだけになる。

- 非常に端的に書く。何が問題か、どうしてほしいかを 1 文で。丁寧語で、前置き・あいさつ・根拠の説明は書かない (根拠は指摘の詳細に書く)。
- 直し方が 1 行の置き換えで決まるときは、文の後に ` ```suggestion ` のフェンスで置き換え後の行を書く。作者は ADO の「Apply change」でそのまま取り込める。複数行にまたがる直しは suggestion にせず文だけにする。
- 属性値は HTML エスケープし、改行は `&#10;` にする。
- `line` の無いリンク (ファイル全体の指摘) と、`unverified` の指摘には付けない。
- 生成するときに PR へ投稿はしない。投稿するかはリンクを押す人が決める。

例:

```html
<a href="{PR の URL}?_a=files&amp;path=%2Fsrc%2Fsync.ts&amp;line=42&amp;lineStartColumn=1&amp;lineEnd=43&amp;lineEndColumn=1"
   data-ado-comment="空配列のとき items[0] で落ちます。長さを確かめてください。&#10;```suggestion&#10;  const first = items.at(0) ?? null;&#10;```">src/sync.ts:42</a>
```
